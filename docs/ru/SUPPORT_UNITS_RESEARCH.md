# Support Units в HWRM/HWMP — исследование 27 октября 2026

[English summary](../SUPPORT_UNITS_RESEARCH.md)

## Вывод и граница результата

**Общий взвешенный бюджет флота выглядит реализуемым средствами моддинга HWRM.** Наиболее убедительная основа — штатные supply-категории, позволяющие одному кораблю расходовать несколько лимитов с разными весами. Информационный счётчик СУ также выглядит достижимым. Полная система HWC с расширением ёмкости носителями/модулями, резервированием очередей и ограничением захвата остаётся отдельной задачей.

Это вывод по определениям и документации, **не подтверждение работающего режима в движке**. В этой работе не собирались BIG, не менялись установленные пакеты, не запускались игра/лаунчер, не обновлялись Workshop и зависимости потребителей. Текущий обычный баланс HWMP сохранён.

Исследование относится к владельцу общей механики — `hwrm-mp-patch`, целевая основа HWMP 2.4.1. Собственные цены/корабли HW1 Nova Races принадлежат следующему слою. Сомтаау и Тварь в эскизе рассматриваются как материал дизайна; их перенос в HWMP этим не разрешён и не выполняется.

## Что именно означает эскиз

Все **101 заполненная строка** переписаны в [sketch.json](../../research/support-units/sketch.json), с сохранением буквальных английских названий и чисел, включая `ClockedF.`. Пустые ячейки не превращены в бесплатные корабли.

Дмитрий подтвердил 27 октября: **`2|14` — 2 СУ за один корабль, 14 за полный отряд из семи кораблей**. Стоимость индивида и отряда взаимосвязана. Никакого выбора между альтернативными ценами эта запись не означает.

Отдельно остаётся выбрать правило для неполного отряда:

- **По живым корпусам:** после потери трёх из семи кораблей отряд расходует 8 СУ вместо 14. Нужен достоверный подсчёт физических корпусов и решение о резерве на пополнение.
- **По полной штатной численности существующего отряда:** расход остаётся 14 до его полной гибели. Это резерв места для восстановления; такое правило проще согласовать со штатным восстановлением эскадрилий.

Освобождать СУ после каждой потери, позволять занимать их новыми кораблями, а затем бесконтрольно восстанавливать старый отряд нельзя: получится обход лимита. Для первой версии рекомендован расход по полной численности существующего отряда. Это предложение, не утверждённое правило.

СУ лучше считать условной нагрузкой на обеспечение флота. Исторический размер экипажа может служить ориентиром, но не должен автоматически определять игровой вес: дроны, автоматизация, оружие и способности существенно различаются.

## Проверенные источники

1. **Оригинальное руководство HWC**, печатная стр. 47 (PDF page index 46): отдельно описаны используемые СУ, резерв в очереди строительства, оставшаяся ёмкость и её увеличение носителями/модулями. Печатная стр. 42 описывает невозможность захвата при нехватке СУ и нанесение урона вместо заражения. Это показывает, какие части механики нужны для полного воспроизведения HWC. [Руководство](https://homeworldarchives.com/media/Homeworld-Manual-Cataclysm.pdf).
2. **Описание HWRM 2.0 участниками разработки модов** прямо указывает дробные веса нескольких supply-категорий и возможность задавать партии из семи кораблей расход как у пяти. Там же отмечено появление жёстких пределов популяции. [Архив исходного обсуждения Gearbox](https://web.archive.org/web/20220720015354/https://forums.gearboxsoftware.com/t/hwr-2-0-modding-changes/1501768).
3. **Karos Graveyard:** назначение `setSupplyValue` — стоимость корабля в supply-категории; `supplyLimit` задаёт её лимит. [setSupplyValue](https://github.com/HWRM/KarosGraveyard/wiki/Function%3B-setSupplyValue), [supplyLimit](https://github.com/HWRM/KarosGraveyard/wiki/Function%3B-supplyLimit). Старый tutorial UnitCaps преимущественно описывает HW2 Classic и не является достаточной инструкцией для HWRM 2.x.
4. **Действующие локальные определения:** stock + закреплённый Test21 + overrides HWMP 2.4.1. Это основное доказательство применимости механизма к нашему проекту.
5. **Отчёт автора No Unit Caps 2.0 от 2016 года** сообщает эффективный предел 250. Это первичное наблюдение автора того мода, но не доказательство значения предела для новой категории СУ в текущем движке. [Страница автора](https://steamcommunity.com/sharedfiles/filedetails/?id=485998120).

Не делаем вывод «в Lua можно написать 1000, значит движок разрешит 1000». Также нельзя считать отсутствие найденного API доказательством принципиальной невозможности.

## Что уже есть в HWRM

В исходниках используются:

```lua
-- Hgn_Interceptor: исходные настройки полной партии
NewShipType.SquadronSize = getShipNum(NewShipType, "SquadronSize", 1)
NewShipType.buildBatch = getShipNum(NewShipType, "buildBatch", 5)
setSupplyValue(NewShipType, "Fighter", 5.0)
setSupplyValue(NewShipType, "Interceptor", 5.0)
setSupplyValue(NewShipType, "LayoutFighter", 5.0)
```

У `vgr_interceptor` явно указаны партия 7 и расход Fighter 5; у `tai_interceptor` — Fighter 1, без явной партии в этом определении. Поэтому штатное Fighter supply нельзя считать ни СУ, ни универсальным физическим числом кораблей.

`scripts/familylist.lua` содержит реестр `unitcapsFamily` с именем, порядком и локализованной подписью; `scripts/rules/deathmatch/unitcaps/normal.lua` задаёт общий профиль, а race-specific файлы меняют отдельные пределы. `supplyShow` управляет отображением строк. `ui/newui/unitcapinfopopup.lua` содержит шаблон строки текущего/максимального расхода.

**Предлагаемая конструкция:** зарегистрировать новую категорию `HWMP_SupportUnits`, назначить каждому учитываемому типу вес, задать общий предел и показать строку «СУ». Имя рабочее, не принятое техническое соглашение. Пример расхода 15/14/80 для Hgn Interceptor / Vgr Assault Craft / Destroyer предполагает, что нативная категория списывает вес за учётный отряд. Именно эту единицу списания сначала нужно измерить.

Для режима СУ старые классовые и корабельные боевые ограничения должны перестать связывать состав флота. Просто спрятать строки через `supplyShow` недостаточно. Категории `Layout*` нужны строям; их нельзя массово менять вместе с ограничениями производства. Аналогично `BuildFamily`, `DisplayFamily`, броня и атакующие классы не являются ценой СУ. Ограничения уникальных объектов и слот исследований имеют отдельный смысл и могут сохраниться.

В бинарном файле обнаружены имена `setSupplyValue`, `supplyLimit`, `supplyShow`, `supplyDesc`, `supplyIndent`. Это подтверждает наличие имён, но не корректность произвольной сигнатуры/области вызова.

## Два пути к счётчику

| Вариант | Преимущество | Что ещё требуется |
|---|---|---|
| Дополнительная штатная supply-категория | Учёт и вывод строки могут выполнять сами механизмы лимитов; меньше собственного состояния | Проверить новую семью, верхний предел, очереди, списание потерь и отсутствие влияния на обычный режим |
| Пересчёт в SCAR/Lua по типам принадлежащих игроку кораблей | Можно показывать номинальный вес, сохраняя прежние лимиты; при отсутствии runtime-цен это отдельная таблица | Откалибровать единицу count, показать неполноту покрытия, проверить dock/hyperspace/захват и мост к HUD |

Для второго пути кандидат — `Player_GetNumberOfSquadronsOfTypeAwakeOrSleeping(player, type)`. Имя есть в текущем EXE и функция используется исходными скриптами. Нельзя умножать её результат на СУ за корпус без калибровки. `SobGroup_Count` тоже не доказывает число корпусов внутри отряда. `Player_NumberOfAwakeShips` не выглядит достаточной основой полного счётчика из-за спящих/состыкованных объектов.

`GetUnitCapFamilyId`, `GetUnitCapForFamily`, `GetUnitCapMaxForFamily` реально используются штатным **AI build manager**, но их доступность в SCAR или UI не доказана. Обнаружение строк в EXE не делает эти функции универсальным getter для HUD. Выдуманный `Player_GetSupportUnits` не предлагается.

Расчётный счётчик стоит пересчитывать из текущего владения примерно раз в секунду, а не вести только накопитель событий стройки/гибели. Тогда захват/передача и загрузка сохранений меньше зависят от пропущенных событий. Однако поведение самого getter на этих переходах всё равно проверяется. Цена неизвестного типа должна давать явный статус «неполный расчёт», а не 0.

По умолчанию показываем только собственный флот локального игрока. Таблица СУ противников может раскрывать информацию сквозь туман войны; зрительский/общедоступный режим требует отдельного решения. В multiplayer локальный UI не должен решать, что разрешено строить: ограничения симуляции одинаковы у всех участников.

## Постоянная и растущая ёмкость

**Постоянный общий бюджет** — лучший первый эксперимент: меньше состояний и проще сравнивать флотилии. Полную систему HWC пока нельзя обещать.

В старых определениях носителей/материнских кораблей встречается `addedUnitCaps=101`. Само наличие присваивания не доказывает работающий поставщик произвольной supply-категории; точное имя не обнаружено при поиске ASCII-строк текущего EXE. Это лишь повод проверить старое поле отдельно, не основание его использовать в дизайне.

Надёжный динамический API изменения лимита выбранной семьи игрока в изученных исходниках не установлен. Отрицательные supply-веса, фиктивные потребители и выдача исследований для имитации ёмкости остаются гипотезами. У них нужны проверки удаления/потери носителя, сохранений, одновременной стройки и сетевой синхронизации.

Если постоянный бюджет выше допустимого движком значения, можно исследовать общий масштаб: например, `1 внутренняя единица = 8 СУ`, тогда 1000 СУ = 125 единиц, корабль за 3 СУ = 0.375. Дробные веса документированы, **но** точность границ, списание и отображение требуют теста. Нативный шаблон текущего расхода использует `%d`; корректный вывод исходных СУ понадобится решать отдельно. Масштабирование не доказывает обход иных жёстких пределов числа объектов.

Нельзя выдавать надпись «СУ / ёмкость» за реализацию полноценного ограничения: важны также резерв очереди, параллельные производители, пополнение и захват.

## Предварительный разбор баланса

Скриншот — полезная первая шкала, но не готовый баланс текущего HWMP. Автоматический аудит показывает:

- Hgn Interceptor: **3 × 5 = 15 СУ**, Vgr Assault Craft: **2 × 7 = 14 СУ**. Это сопоставимые цены полных партий при разном числе корпусов; одинаковая цена за корпус не обязательна.
- Hgn Gunship: **4 × 3 = 12**, Vgr Missile Corvette: **3 × 4 = 12**. Есть понятная идея одинаковой цены сравнимых партий.
- Vgr Bomber: в эскизе **2 × 7 = 14**, а исходный `buildBatch` сейчас **6**. При сохранении цены за корпус получится **12 СУ** за штатную партию. Выбор 12 или 14 должен быть явным; размер партии не меняем автоматически.
- У таиидан эскиз подразумевает собственную линейку лёгких/тяжёлых перехватчиков, эсминцев и Защитников. Сопоставления со stock IDs помечены как кандидаты, а не как тождество ролей. Например, нельзя автоматически выдать stock тяжёлому крейсеру цену «Heavy Destroyer 90» и считать его тем самым новым кораблём.
- Кушанской колонки нет. Для неё нужно отдельное назначение весов, включая научные корабли и управляемые дроны.
- Нет завершённой политики материнских кораблей, носителей, верфей, их вклада в ёмкость и стоимости научных пристыковываемых частей. Сначала разделяем неизвестное, намеренно бесплатное и внутренний зависимый объект.

При текущих исходных RU-ценах Hgn/Vgr Destroyer стоит 2000 RU при эскизных 80 СУ, Battlecruiser — 4000 RU при 150 СУ, Hgn Torpedo Frigate — 700 RU при 12 СУ. Получается 25 / 26.67 / 58.33 RU за СУ. Это **не коэффициент боевой эффективности**, но показывает: одинаковый бюджет открывает намного больше вложений RU во фрегатную массу. 150 СУ позволяют иметь 12 таких фрегатов (144 СУ, 8400 RU) либо один линейный крейсер (150 СУ, 4000 RU), без учёта инфраструктуры/исследований. Это тестовая развилка, а не доказательство превосходства одной стороны.

Пример только арифметики: 20 сборщиков по 4 СУ + 2 контроллера по 13 = **106 СУ экономики**. При условном общем бюджете 500 останется 394 СУ **до неоценённой инфраструктуры**. Два крейсера по 150 оставят 94; четыре эсминца по 80 — 74. Бюджет 500 здесь иллюстративный и не предложен как готовая настройка или допустимое нативное число.

Основные риски тестовой шкалы:

1. **Масса дешёвых фрегатов и платформ.** Платформа за 2 СУ может насыщать карту объектами значительно раньше, чем исчерпается боевая масса крупных кораблей. Помимо СУ нужен отдельный технический предел объектов, не объявляемый балансом классов.
2. **Поддержка и захват.** DFF, ремонт, гравитация, маскировка и захват могут усиливать флот нелинейно. Снятие нынешних subcaps без проверки создаёт совершенно другой режим.
3. **Экономика занимает военное место.** Это интересный выбор «добыча или армия», но при полном лимите может мешать восстановить потерянную экономику. Нужно проверить экономические рейды и возможность заменить сборщики.
4. **Нулевая цена зондов не означает бесконечные зонды.** Можно оставить их 0 СУ по эскизу и сохранить технические/типовые ограничения явно. Исследовательские части и дочерние дроны требуют своей политики, чтобы не считать родителя и содержимое дважды.
5. **Поздние технологии и пополнение.** Фиксированная цена СУ может сохраняться после улучшений, но тогда сравнивать нужно ранние и полностью улучшенные флоты. Для частичных отрядов отдельно проверяется резерв места.

Рекомендую начинать с Hgn↔Vgr и сохранять текущие RU/время/оружие. Менять только СУ и изучать: равные RU, равные СУ и равные RU+СУ; доступные составы, темп выхода, восстановление после потерь, захват и поддерживающие стеки. По итогам повторяемых матчей корректировать веса, а не пытаться вывести всё из экипажа или одного DPS/HP.

## Минимальный эксперимент и критерии

Рекомендуемая следующая задача — **изолированный прототип счётчика и небольшой полигон фиксированного лимита** с уровнем усилий **High**. Подготовка кода сама не разрешает установку/запуск. Medium подойдёт для дальнейшего заполнения цен и отчётов после установления механики; Extra High оставляем для выявленной сложной проблемы движка/синхронизации.

| Проверка | Что измерить |
|---|---|
| Новая категория | Регистрация новой семьи, подпись, нулевая начальная строка; отсутствие ошибок загрузки |
| Единица списания | Один эсминец; одна партия Hgn 5 и Vgr 7; сравнить native cap, getter, видимые корпуса |
| Потери и Dock | Потерять часть партии, состыковать/восстановить, уничтожить остаток; расход и резерв |
| Очереди | 2–3 производителя на общей границе; отмена, пауза, потеря производителя, queued vs active |
| Предел | Проверить граничные расходы около 250/500/1000 и дробные эквиваленты; не только текст на экране |
| Владение | Захват, передача союзнику, потеря последнего носителя, hyperspace; не исчезает ли цена |
| Сохранения | Свежая запись/загрузка и новый процесс: world и расчёт возвращаются к одной точке |
| Изоляция | Обычные HWMP game types и stock кампании не получают новых лимитов/весов |
| Multiplayer | Два клиента с одинаковыми архивами, одновременные очереди, одинаковое состояние; отсутствие утечки чужого флота в HUD |

Первый прототип может оставить все классовые ограничения и только показывать номинальные СУ. Полноценный режим следует после доказательства списания/резервов и выбора правил. Отдельный Game Type должен иметь собственную идентичность и проверенную загрузку профилей; одно наличие новых `.ship` в пакете не изолирует их от обычного режима. Способ условного подключения весов нужно проверить на этапе загрузки статических корабельных определений, не переключать их периодическим Lua-таймером.

## Воспроизводимость

Инструмент [audit_support_units.py](../../tools/audit_support_units.py) только читает эффективные определения через существующий пассивный инспектор. Он записывает отчёт и каталог, не вызывает сборку или исполняемый файл игры.

```powershell
python tools/audit_support_units.py
```

Начальный запуск: 101 строка эскиза, 126 уникальных ship types из четырёх build tables, 142 хешированных входа. Ни один кандидат привязки эскиза не отсутствует в этих таблицах. Наличие строки build table **не означает доступность в обычном MP**: среди них заблокированные специальные корабли и внутренние дроны.
